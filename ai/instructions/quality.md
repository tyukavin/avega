# Качество и проверка

## Контракт компонента

- Перед созданием или существенной переработкой компонента определи его назначение, обязательную разметку, допустимое содержимое и границы ответственности.
- Зафиксируй базовый БЭМ-блок, элементы, модификаторы, состояния `is-*` и JS-контракт через `data-*`.
- Предусмотри состояния загрузки, ошибки, отсутствия данных, длинного контента и отключённого JavaScript, если они применимы.
- Компонент не должен зависеть от конкретной страницы, порядка соседних блоков или внешнего контекстного селектора.
- Публичные классы, `data-*`-атрибуты и события компонента изменяй осознанно: их изменение может нарушить шаблоны, стили и JavaScript.

## Производительность

- Не ухудшай метрики LCP, CLS и INP без обоснованной причины. При изменении первого экрана, изображений или интерактивности оцени влияние на эти метрики.
- Не загружай заранее тяжёлые изображения, скрипты и стили, которые не нужны для первой отрисовки.
- Используй предусмотренную сборкой оптимизацию изображений и современные форматы. Для разных размеров изображения применяй подходящий адаптивный источник, когда это даёт заметную экономию.
- Подключай только используемые начертания и форматы шрифтов; не задерживай отображение текста ненужными ресурсами.
- Не добавляй стороннюю библиотеку ради поведения, которое надёжно реализуется небольшим объёмом нативного кода. Исключение для каруселей: только Swiper.js с соблюдением требований раздела 3.6.
- Избегай частых синхронных измерений и изменений DOM в цикле, которые вызывают повторный layout.
- Оптимизация не должна ухудшать семантику, доступность, читаемость кода и устойчивость интерфейса.

## Процесс проверки

Проверка обязательна для каждой задачи и должна подтверждать выполнение всех применимых требований, а не только отсутствие ошибок сборки. Нельзя сообщать о завершении работы, пока остаются известные нарушения инструкций.

### Проверка соответствия инструкциям

- Перед завершением повторно прочитай инструкции и сопоставь каждый изменённый HTML-, SCSS- и JavaScript-файл с соответствующим разделом.
- Проверь не только добавленные строки, но и затронутый компонент целиком: его шаблон, стили, состояния, поведение и связи с соседними компонентами.
- Убедись, что новое решение не создаёт исключений из БЭМ, семантики, доступности, системы токенов, модульности JavaScript и правил зависимостей.
- Исправь найденные нарушения до завершения задачи, включая нарушения, появившиеся косвенно из-за внесённых изменений.
- Если требование неприменимо, проверка может быть пропущена только осознанно. Если выполнить требование невозможно, явно укажи причину и оставшийся риск в результате работы.

### Автоматические и ручные проверки

- Запусти линтеры и сборку для всех затронутых типов файлов. Перед завершением задачи с изменением исходного кода выполни `npm run check`.
- Успешные линтеры и сборка не заменяют ручную проверку семантики, доступности, адаптивности и поведения.
- Проверь страницу в браузере в сценариях, затронутых задачей, включая пограничные состояния и отсутствие JavaScript, когда контент должен оставаться доступным.
- Не оставляй отладочные сообщения, временные данные, закомментированный код, неиспользуемые стили и мёртвые ветви логики.
- В итоговом сообщении перечисли выполненные проверки. Если какую-либо обязательную проверку запустить не удалось, укажи её название, причину и что осталось непроверенным.

### Критерий готовности

Работа считается завершённой только когда одновременно выполнены следующие условия:

- результат соответствует задаче и исходному макету;
- выполнены все применимые требования инструкций;
- разметка семантична и доступна с клавиатуры и для вспомогательных технологий;
- интерфейс устойчив на поддерживаемых ширинах, при длинном контенте и изменении масштаба;
- обе темы и все состояния компонента проверены, если они входят в задачу;
- сборка и обязательные автоматические проверки проходят без ошибок;
- в консоли браузера нет ошибок и необработанных исключений;
- отсутствуют известные дефекты, временные решения и необъяснённые отклонения от инструкций.

## CI/CD

- `.github/workflows/check.yml` запускает `npm run check` при push в `main` и для pull request.
- CI выполняет ту же проверку, что и локальная команда `npm run check`: форматирование, линтеры, сборка и HTML-валидация.
- Если проверка назначена обязательной в настройках защиты ветки, её падение блокирует merge. Перед пушем всегда выполняй `npm run check` локально.
